# 取词管线「仿原生」架构说明

本文档记录:**为什么不用 PDFKit 原生选择**、**开源候选的调研结论**、以及**自研管线是如何"仿照原生"的**(哪些用了系统真件、哪些是对标实现、哪些是刻意保留的差异)。

## 1. 为什么不直接用 PDFKit 原生选择

- iOS 18 起 PDFKit 存在已知回归,至 18.4 仍未修复:
  - `PDFPage.characterBounds(at:)` 返回错误坐标(开发者反馈 FB14843671);
  - `page.string` / `attributedString` 文本顺序错乱,部分文本跑到页面末尾附近(FB16264926)。
- 本项目真机实证(两个样本 PDF,均为非线性化结构:FreePic2Pdf 扫描书 / iText+InDesign 教材):
  - 触发原生选择后 **52ms 内跳到文档最后一页**,并伴随 **6 秒级卡死**;
  - 换上"规范化读取副本"后仍会复现(规范化只解决了一部分)。
- 结论:**原生选择机制在异常文本层文档上不可用** → 采用自研管线,但原则是
  **"能用的系统公开组件就用系统件,行为逐条对标原生"**。

## 2. 开源候选调研结论(2026-10)

| 候选 | 结论 |
|---|---|
| PSPDFKit / Nutrient | 商业授权,排除 |
| PDFium(Chrome 的 PDF 引擎,BSD-3) | 只是"引擎",不带选择 UI;prebuilt xcframework 可用(espresso3389/pdfium-xcframework)。**若未来需要索引级文本能力**(全文检索、跨页整句等),可作为文本层升级件;当前点坐标管线不需要 |
| MuPDF | AGPL,许可不合要求 |
| pdf.js | Web 栈;需把阅读器整体搬进 WKWebView,Pencil 集成与原生体验难保证 |
| PDFEditorSDK(MIT,小型项目) | 只有批注/画笔能力,无文本选择;可作为 M4 铅笔标注模式的参考 |
| VisionKit Live Text(`ImageAnalysisInteraction`) | 系统级取词(真·原生件,支持自定义菜单项插入),但要求把页面渲染为位图 + 每页 Vision 分析,缩放清晰度/性能/铅笔支持均有代价,不适合当前"矢量渲染阅读器"形态(备选实验) |
| `UITextInteraction` + `UITextSelectionDisplayInteraction` | 真·原生选择组件链,但需要完整的 `UITextInput` 一致性实现;在受限 PDF 上索引级文本不可靠 → 需先引入 PDFium 级文本层(大工程,列为后续选项) |

## 3. 我们现在用的"系统真件"

- **`UITextLoupeSession`**(iOS 17+,任意视图可用):**系统放大镜**——拖动选词 / 拖柄 / 拖选区时实时跟随;
- **`UIEditMenuInteraction`**:编辑菜单**就是系统原生菜单组件**(弹出动画、位置、键盘导航均由系统负责);
- 其余(手势识别、选区几何、高亮绘制)自研,行为逐条对标原生。

## 5. 有意保留的差异(原因)

1. **拖动按词粒度吸附**(原生为字符粒度):iOS 18 起字符索引 API 不可靠;词粒度同时更符合"取词"产品语义。
2. **拖动/长按期间冻结滚动**(原生支持贴边自动滚动):历史 bug(拖动被滚动抢走、跳页)的稳定器。
3. **三击 = 整行而非段落**:PDF 没有可靠段落结构,行是安全近似。
